# Offline evaluation capacity on October 14, 2026

The installed `sentinel-eval` CLI passed the predeclared offline protocol at all
tested levels, through **eight concurrent workers**, with zero unexpected errors.
The five-minute, two-worker stage validated **2,606 batches** at **8.684 batches/s**.
Each batch contains 120 synthetic runs, so that stage represents 1,042 evaluated
fixture runs/s. These are local fixture evaluations, not model requests or hosted
customer throughput.

The limit tested was eight workers. **Saturation under the protocol's latency,
error and memory criteria was not reached at that bound.** The four-worker stage
had the highest observed throughput, 11.565 batches/s; eight workers achieved
8.694 batches/s with higher latency. The shared desktop was not controlled, so
this observation does not isolate an application bottleneck or establish the
best deployment size. No code optimization is justified by this run alone.

All seven stages passed their applicable latency, error, throughput and memory
criteria. There were 3,903 validated normal-stage batches, three warm-ups, ten
expected rejections, and ten subsequent valid recovery batches: 3,926 recorded
operations in total. Warm-ups and deliberate failure operations are excluded
from the stage throughput table. Percentiles use nearest-rank on every attempt,
including errors if present; throughput counts only validated batches.

At eight workers, the conservative sum of worker peak-memory values was
280.33 MiB, below the 4,096 MiB criterion. Maximum individual evaluator memory
across the normal stages was 35.30 MiB; the harness peak was 22.94 MiB. These are
per-process measurements, not whole-machine or container memory limits.

Five missing-file attempts and five malformed-file attempts returned exit 2
while preserving both seeded output files byte for byte. Every subsequent valid
batch passed. The slowest expected rejection took 0.336 seconds and the slowest
recovery batch took 0.523 seconds, within the ten-second criterion. This tests
local file dependencies, not database or network failover.

No paid infrastructure or external model calls were used. Currency cost per
successful operation is **unavailable**, not zero: local hardware and energy
were not priced. Cost and latency fields inside the sample evaluation report are prewritten
fixture values, not expenses or durations observed by this benchmark.
CPU seconds per validated batch are shown separately; they do
not establish customer savings or cloud cost.

`summary.json`, the predeclared criteria snapshot, exact generated inputs, one
compressed validated sample report, the compressed raw operation log and `SHA256SUMS`.
Only the local wheel URL in the published summary was shortened to its basename.
All measured values and hashes remain unchanged. The raw operation log retains
each result, timing, resource measurement and report hash; passing report pairs
other than one sample per stage were removed after validation during the run.

From that directory, verify the files and uncompressed operation log:

```bash
shasum -a 256 -c SHA256SUMS
python3 - <<'PYVERIFY'
import gzip, hashlib, json

summary = json.loads(Path('summary.json').read_text())
data = gzip.decompress(Path('operations.jsonl.gz').read_bytes())

rows = [json.loads(line) for line in data.splitlines()]
assert len(rows) == 3926
assert all(row['ok'] for row in rows)
print('Recorded operations and digest verified:', len(rows))
PYVERIFY
```

## What remains unestablished

This single short experiment does not establish production capacity, maximum
saturation, long-term reliability, PostgreSQL or Aegis performance, diverse trace
sizes, independent maintainability, or user benefit. Before changing concurrency
or optimizing an implementation, repeat the same protocol on controlled hardware
and profile the measured constraint. Keep any new workload criteria separate.
